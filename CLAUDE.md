# Editor de Vídeos

App local que transforma clipes em um vídeo vertical 1080x1920 editado. O sistema tem duas partes: uma **API FastAPI** em `API/`, com todo o processamento, e um **frontend web** em `frontend/`, que só conversa com a API.

O plano, as decisões fixas e o checklist ficam em `etapas.md`, que é a fonte da verdade. Implemente uma etapa por vez com a skill `etapa-workflow`. Testes que dependem de vídeos do usuário ou de checagem manual ficam em `testes-pendentes.md`.

## Layout
- `API/`: backend Python 3.12 com `uv`: `src/` (núcleo + `src/api/`), `tests/`, `pyproject.toml`, `.cache/` e `data/` (projetos da API). **Todo comando `uv` roda dentro de `API/`.**
- `frontend/`: Vite + React + TypeScript. Todas as chamadas passam por `frontend/src/api.ts`; em dev, o Vite faz proxy de `/api` para `http://127.0.0.1:8000`. O layout (Etapa 10) é o `App.tsx` em grid: cabeçalho, palco (`Stage.tsx`: resultado, clipe ou plano criativo), faixa de clipes (`ClipStrip.tsx`, arrastar para reordenar), coluna de opções e job (`OptionsPanel.tsx` + `JobPanel.tsx`) e barra de projetos (`ProjectBar.tsx`); o `Workspace.tsx` cuida do estado do projeto aberto. Tema escuro com variáveis em `index.css`.
- `samples/` (vídeos de teste do usuário) e `output/` (resultados para conferir) ficam na raiz.
- `.env` na raiz ou em `API/.env`: `config.load_settings` lê os dois, e `API/.env` tem precedência.

## Comandos
- Backend (dentro de `API/`):
  - `uv sync`: instala as dependências. Para usar a GPU no Whisper sem CUDA instalado: `uv sync --extra gpu`.
  - `uv run python -m src.api [--reload]`: sobe a API em http://127.0.0.1:8000 (documentação em `/docs`).
  - `uv run python -m src.doctor`: verifica FFmpeg, GPU, pacotes, chaves e modelo de rosto.
  - `uv run pytest -q`: testes rápidos. Com `-m integration`, roda os lentos (vídeos reais em `../samples`, GPU, LLM pago).
  - CLIs do núcleo:
    - `python -m src.pipeline`: pipeline completo pela linha de comando;
    - `python -m src.transcribe`: transcrição de um clipe;
    - `python -m src.face clipe.mp4 -o debug.mp4`: rastreio de rosto com vídeo de debug;
    - `python -m src.render`: render básico da timeline de um `project.json`, sem os efeitos criativos; use a API ou `src.pipeline` para a geração completa;
    - `python -m src.audio.optimize entrada saida.(wav|mp3)`: limpeza e normalização do áudio.
  - `uv add <pacote>`: adicionar dependência. Nunca edite o `uv.lock` à mão.
- Frontend (dentro de `frontend/`): `npm install`, `npm run dev` (http://localhost:5173, com a API rodando) e `npm run build`.

## Regras que o código precisa respeitar
- O LLM decide *o quê/quando* (índices de palavras, queries); o código decide *onde/como* (geometria).
- LangChain só em `API/src/llm/client.py`; prompts em `API/src/llm/prompts/*.md`.
- Configuração só via `src.config.get_settings()`. O modelo do LLM pode ser trocado por execução em `PipelineOptions.llm_model` (`Settings.for_model`); `GET /api/config` lista os escolhíveis (`Settings.available_llm_models`, só provedores com chave). O python-dotenv lê `KEY=   # comentário` como valor, e `config._clean` trata isso.
- Processamento pesado na API é sempre um **job** (`API/src/api/tasks.py`), numa fila com um worker. Um projeto com job ativo não pode ser alterado (a API responde 409). Toda funcionalidade nova entra no núcleo (`src/`), é exposta na API (com testes em `tests/test_api.py`) e ganha um controle mínimo no frontend.
- Legendas: `.ass` gerado por `src/captions.py` a partir das palavras em t_out, **por clipe** (nunca atravessa emenda), e queimado na passada 2 do render (`_second_pass`, filtro `ass=`). A fonte (Poppins Bold, OFL) fica em `API/fonts/` e é copiada para a pasta de trabalho do render.
- Imagens (`src/images.py`): o LLM só escolhe as palavras e a query; o código faz a validação (densidade, 1,2–3 s, sem atravessar emenda), a busca (Pexels, com o Pixabay como alternativa, e cache) e o posicionamento (zonas livres de rosto e legenda). O plano criativo (imagens + zooms, uma chamada só ao LLM com o prompt `plano_criativo`) fica em `API/data/projects/<id>/plano_imagens.json`: o job `imagens` é a prévia, e o `gerar` reaproveita o plano se a `assinatura` (trechos) não mudou.
- Zooms (Etapa 9): o LLM aponta a palavra de ênfase; `images.validate_zooms` aplica as regras (1 a cada 8 s, 1–2,5 s, sem atravessar emenda). A geometria fica em `src/reframe.py`: `plan_zooms` fixa o pico de cada zoom (até 1,15, limitado para a caixa real do rosto caber com folga; frames sem detecção seguem o caminho da câmera), `zoom_curve` dá a escala por t_out (smoothstep) e `CameraPath.window_f(t, escala)` é a janela fracionária, recortada no render com `cv2.warpAffine` (sem tremor de 1 px). O `face_boxes_fn` recebe a mesma curva, e as imagens desviam do rosto já ampliado.
- Erros e avisos (Etapa 11): o job guarda `src.errors.mensagem_amigavel(exc)` (causa provável + o que fazer, com o detalhe técnico no fim) e o resultado traz `avisos` (sem áudio, fps variável, HDR, rosto quase não detectado) e `llm` (chamadas, tokens e custo estimado por `src/llm/pricing.py`). Etapas longas recebem `on_progress(fracao)`, que também cancela (o `ctx.step` lança): quem chama o callback precisa deixar a exceção passar — o Whisper marca com `_ProgressoAbortado` para não cair no fallback GPU→CPU, e o `render_debug` mata o ffmpeg antes de propagar.
- Fontes difíceis: `probe_clip` marca `vfr` e `hdr`; o render converte HDR para BT.709 com tonemapping e reduz fontes muito maiores que a saída antes do pipe (`_render_segment_reframe`).
- Com `frontend/dist` compilado, a API serve a interface em `/` (`api.app.montar_frontend`).
- Trechos (`Clip.trechos`) ficam na grade de frames (1/30 s): `cuts.TimeMap` e o render produzem exatamente os mesmos tempos.
- Rosto:
  - O mediapipe 1.x não tem `mp.solutions`: use `mediapipe.tasks.python.vision.FaceDetector`.
  - O BlazeFace não enxerga rostos de tamanho normal num quadro 16:9 inteiro; `face.square_crops` resolve isso detectando em recortes quadrados.
  - `FaceTrack.cx/cy/w/h` é o caminho suave da câmera (Etapas 6 e 9); `FaceTrack.box_at(t)` é a caixa real do rosto (Etapas 8 e 9).

## Ferramentas novas (novas-etapas.md)
- O `novas-etapas.md` traz seis frentes em desenvolvimento (áudio, estabilização, b-roll, legendas de destaque, edição pós-render e transições adicionais). Mesma regra: uma etapa por vez, com verificação antes de marcar.
- Áudio (`API/src/audio/`): o DeepFilterNet roda pelo **binário oficial** baixado para `CACHE_DIR/models/` (o pacote do PyPI não tem wheel para o Python 3.12); `metrics.measure` dá piso de ruído, nível de fala e SNR, e é assim que os testes provam que a limpeza funcionou. No pipeline, `PipelineOptions.limpar_audio` troca **só o áudio do vídeo final** (`pipeline.audios_limpos` → `render_timeline(audios=...)`); a transcrição continua com o áudio original, porque medir mostrou que limpar antes de transcrever piora o Whisper. A cadeia é `optimize.optimize_audio`: highpass 80 Hz → `denoise.denoise` (DeepFilterNet → noisereduce → afftdn, caindo para o próximo se um falhar) → `loudness.normalize` (loudnorm em 2 passadas, −16 LUFS), com cache por hash do arquivo + parâmetros + `CADEIA_VERSION`. O cache guarda o motor usado: se ele for pior que o disponível agora (o binário do DeepFilterNet é baixado no 1º uso), a cadeia refaz em vez de devolver o áudio pior; e um download que falhou fica marcado na sessão (`deepfilter.pode_usar`), para não retentar a cada clipe. Depois do loudnorm o ruído absoluto engana (o ganho sobe tudo): compare **SNR** — mas o SNR também engana quando `Medidas.silencio_digital` é verdadeiro (o DeepFilterNet zera o fundo e o número dispara). Para eco, meça a reflexão (autocorrelação no atraso), não o SNR. Os padrões `AUDIO_AGGRESSIVENESS` e `AUDIO_TARGET_LUFS` vêm do `.env` por `AudioParams.do_env()`.
- Estabilização (`API/src/video/`, Parte 2): `stabilize_video(entrada, saida, smoothing, crop_percent, on_progress=..., metodo="auto")` usa `vidstabdetect`/`vidstabtransform` quando disponíveis, ou `opencv_fallback.py` automaticamente sem esses filtros. O fallback rastreia pontos com Lucas-Kanade, estima a transformação afim, suaviza a trajetória, aplica `warpAffine` e recorta as bordas. Ambos copiam o áudio original e guardam MP4 por hash do clipe + parâmetros + **motor** + versão em `CACHE_DIR/video_estabilizado/`. Os níveis leve/médio/forte usam janelas de 11/25/49 frames; os padrões de nível/crop vêm de `STABILIZE_SMOOTHING` e `STABILIZE_CROP_PERCENT`. `API/src/video/cli.py` atende `python -m src.video.stabilize entrada.mp4 saida.mp4 --smoothing medio --crop 5 [--metodo opencv]`; o método usado aparece na saída e o progresso acompanha as duas passadas. No editor, `PipelineOptions.estabilizar` cria uma cópia do projeto com caminhos de vídeo estabilizados antes de `face_tracks` e do render; transcrição, cortes e plano criativo continuam no projeto original. `Project` salva a opção e o nível.
- B-roll (`API/src/broll/`, Parte 3): `PlanoImagens.broll` guarda cutaways planejados junto a imagens e zooms. `plan_broll_project` recebe as palavras globais em `t_out`, segmenta frases por pontuação, pausas e emendas entre clipes ou entre trechos cortados do mesmo clipe (`PalavraGlobal.segmento`) e usa `llm/prompts/plano_broll.md` para selecionar frases e queries. A validação exige as bordas exatas da frase, 1,5–4 s, intervalo configurável entre inícios (8–30 s), retorno à câmera e ausência de imagem sobreposta. `source.prepare_broll(query, duracao)` busca Pexels Videos e tenta Pixabay Videos quando necessário, exige relevância mínima pelo título/tags, baixa MP4 até 1920 px na maior dimensão, normaliza para 1080x1920 a 30 fps sem áudio e guarda o resultado por query e duração em cache; retorna `None` quando não encontra clipe utilizável. `render_timeline(..., broll=...)` substitui só os quadros após o reenquadramento e o zoom; `broll_transition` escolhe corte seco (padrão), crossfade, deslizamento ou varredura de 0,25 s. O áudio AAC concatenado é copiado sem recodificação. A validação impede cutaways sobrepostos ou atravessando emendas entre trechos/clipes. O job `broll` planeja e prepara clipes para prévia sem render; `GET/PATCH /api/projects/{pid}/broll` mostra frase, query, duração e vídeo, e aceita aprovar, alterar query ou desativar. Cada item começa não aprovado; só itens aprovados entram no render final. Nova busca usa o plano salvo sem chamar o LLM outra vez. A UI mostra o vídeo na tela do plano criativo e salva ativação, densidade e transição no `project.json` ao iniciar um job. No render, imagens ativas prevalecem sobre B-roll conflitante e zooms cobertos não são usados. A Parte 6 planeja efeitos adicionais.
- Legendas de destaque (`API/src/highlight_captions/`, Parte 4): `planner.plan_highlights_project` usa as palavras globais já cortadas em `t_out`, divide frases sem cruzar clipes nem trechos mantidos e consulta `llm/prompts/plano_destaques.md`. O LLM escolhe um trecho literal de até cinco palavras consecutivas dentro de uma frase; `validate_highlights` rejeita reescrita, duração fora dos limites, emendas, vizinhança e falta de espaço para a permanência. O cache do LLM inclui prompt, modelo, roteiro, palavras com índices e limites. `ass_builder.write_highlights_project` gera um `.ass` separado das legendas contínuas: revela palavras em seus tempos, mantém o trecho pelo tempo configurado (1,2 s padrão) e aplica fade. O estilo padrão usa 72 px na base 1080x1920 e escolhe uma área livre; `caixas_ocupadas` permite desviar dos rostos e das imagens no intervalo do destaque. O builder rejeita planos antigos com mais de cinco palavras, emendas e cortes fora da grade de quadros. `PipelineOptions` e `Project` têm `legendas_continuas`, `legendas_destaque` e `estilo_destaque`; a validação impede ambas as modalidades simultâneas, inclusive ao carregar/salvar o projeto. O pipeline replaneja destaques antigos ou com permanência alterada, gera o ASS do modo escolhido e o frontend usa um seletor único Nenhuma/Contínua/Destaque com ajustes de duração, tamanho e cor.

- Documento de edição (`API/src/editing/project_schema.py`, Parte 5 Etapa 0): `Project` v2 guarda `documento.elementos` com IDs estáveis, tipo, intervalo em `t_out`, estado e dados completos. Clipes e cortes vêm da timeline; imagens, zooms, B-roll e destaques vêm do plano criativo; crops são keyframes da câmera e legendas contínuas vêm dos eventos `.ass`. `ProjectStore.load_plan/save_plan` lê/escreve o plano no `project.json`; o sidecar antigo só é importado ao migrar v1 e, quando já existe, espelhado para compatibilidade. A migração automática cria `project.v1.json` como backup; `python -m src.editing.migrate` migra todos os projetos salvos. Alterar cortes marca elementos visuais anteriores como obsoletos até novo planejamento/render. `src.render` permanece uma ferramenta de baixo nível para a timeline sem efeitos criativos.
- Render incremental (`API/src/editing/segments.py` e `incremental_render.py`, Parte 5 Etapa 1): o job `gerar` divide cada trecho mantido nas bordas dos elementos e em lacunas de até 3 s. O hash inclui fonte, áudio, câmera/zoom, elementos, efeitos e eventos `.ass` que realmente incidem no segmento; MOVs prontos ficam em `API/data/projects/<id>/render_cache/`. O job aceita `ids_alterados` no corpo e retorna `segmentos_renderizados`/`segmentos_reutilizados`; o manifesto anterior também invalida intervalos de IDs removidos ou movidos. A montagem final copia os quadros H.264 e codifica o áudio uma vez. Fades de áudio só entram nas emendas reais, não nas divisões para cache. A CLI `src.pipeline` continua com o render tradicional.
- Substituição pós-render (`API/src/editing/replace.py`, Parte 5 Etapa 2): `POST /api/projects/{pid}/replace/{element_id}` aceita busca nova ou índice de alternativa; `.../upload` aceita arquivo próprio. Ambos criam job `substituir`, que reutiliza opções da última geração, mantém cortes/timeline e chama o render incremental com o ID alterado. Imagens do usuário ficam em `uploads/replacements` do projeto e passam pelo preparo usual de overlay; vídeos são normalizados e guardados no cache de B-roll. Alternativas de imagem já estão no plano; alternativas de B-roll são registradas na prévia para não repetir a busca. O job só salva a mudança se o efeito substituído entrou no render. A interface expõe a troca no plano criativo e atualiza o player ao terminar.
- Histórico pós-render (`API/src/editing/history.py`, Parte 5 Etapa 3): cada troca concluída guarda a versão anterior e a nova em `.history/v*.json`, com resumo/IDs alterados e SHA-256 do MP4 em `index.json`. `rendered.json` registra qual documento corresponde ao MP4 atual; troca com prévia pendente é rejeitada até uma nova geração. `GET /api/projects/{pid}/history` lista versões; `POST .../undo` e `.../redo` criam jobs que restauram o `project.json` e renderizam incrementalmente os IDs afetados, exigindo que o MP4 gerado seja idêntico ao da versão salva. Uma edição após desfazer descarta o ramo de refazer; nova geração integral zera o histórico. `HISTORY_MAX_VERSIONS` (padrão 20, intervalo 2–100) limita as versões por projeto. O frontend mostra Desfazer/Refazer no resultado.
- UI de edição pós-render (`API/src/editing/preview.py`, `API/src/api/routes/editor.py`, Parte 5 Etapa 4): `GET /api/projects/{pid}/editor` lista imagens, B-roll, zooms e destaques por ID e tempo para a nova aba Edição. `POST .../{element_id}/preview` e `.../preview/upload` criam o job `previsualizar`, que renderiza só o trecho afetado em até 360x640, sem áudio, numa pasta temporária e sem alterar o vídeo final. A proposta guarda hashes do documento e MP4; `POST .../previews/{token}/apply` cria `aplicar_edicao`, rejeita propostas obsoletas, faz render incremental final, atualiza o documento e registra a versão no histórico. Remoção desativa o item mantendo o ID. A aba Plano criativo conserva a troca direta da Etapa 2; a aba Edição oferece prévia antes de aplicar.
- Ferramentas do chat (`API/src/editing/chat/`, Parte 5 Etapa 5): seis schemas Pydantic expõem listar, remover, trocar imagem, ajustar duração, limitar intensidade de zoom e mover elementos por ID. `EditSession` trabalha em cópia do projeto e valida duração, densidade, sobreposição, emendas e efeitos habilitados antes de aceitar cada ação; B-roll só é encurtado em fim de palavra da frase original quando o worker fornece a transcrição. A intensidade individual do zoom fica em `ItemZoom.intensidade` e limita o pico seguro no render. `chat/agent.py` executa um loop curto e guarda ações propostas, sem publicar o MP4; a chamada `.bind_tools()` fica isolada em `src/llm/client.py`, com prompt em `src/llm/prompts/chat_edicao.md`. A API, a prévia e a interface do chat pertencem à Etapa 6.
- Interface do chat (`API/src/api/routes/chat.py`, `API/src/editing/chat/history.py`, `frontend/src/components/ChatPanel.tsx`, Parte 5 Etapa 6): a aba Edição mostra a conversa ao lado da linha do tempo, com IDs das ações e prévia curta automática. `POST /api/projects/{pid}/chat` cria o job `conversar`; `GET` devolve histórico e proposta pendente. O agente edita um rascunho com no máximo uma ação por pedido, renderiza apenas o trecho e só modifica o MP4 final após `POST .../editor/previews/{token}/apply`. O estado da conversa fica em `.chat/state.json`; propostas antigas são invalidadas quando o documento muda. Pedidos vagos recebem pergunta de esclarecimento e pedidos de replanejamento apontam os controles de planejamento. A transcrição é carregada sob demanda apenas para ajustar a duração de B-roll.
- Robustez da edição (`API/tests/test_editing_robustness_api.py`, Parte 5 Etapa 7): teste sintético exercita cinco mudanças alternando troca manual e chat sobre duas imagens com B-roll vizinho; compara todos os quadros do cutaway e da lacuna, verifica IDs/documento, manifesto do cache e histórico a cada edição, e confirma Desfazer/Refazer por bytes do MP4. O README explica as seis ações do chat v1 e quando gerar novo plano.
- Catálogo de transições (`API/src/broll/catalog.py`, Parte 6 Etapa 0): inventaria os nomes do `xfade` instalados e define sete presets (corte seco, fusão, deslizamento, varredura, revelação, zoom e desfoque) com nome, descrição, duração, direção, intensidade permitida e custo relativo. `choose` quantiza a duração à grade fixa de 30 fps; `validate_placement` rejeita cutaways curtos, emendas e intervalos insuficientes antes de renderizar. `python -m src.broll.catalog` gera sete prévias sintéticas em `output/parte6_etapa0_catalogo/`, um manifesto com custo medido e uma página HTML para comparar. O render final e a UI desses novos efeitos pertencem às Etapas 1 e 2.
